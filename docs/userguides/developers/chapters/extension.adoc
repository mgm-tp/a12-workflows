= Workflows Extension

[[anchor-workflows-extension-config]]
== Workflows Extension Configuration

NOTE: See also <<anchor-workflows-extension-secure-config, secure configuration>> suggestions for production.

Since this is an extension for Data Services, please also refer to link:/docs/DATA_SERVICES/dataservices-documentation-src/index.html#dataservices-configuration[Data Services configuration,role=internal].

For the Workflows Extension itself, we offer the following configuration options:

[width="100%",cols="25%,25%,25%",options="header",]
|===
| Configuration Property | Default Value | Remarks
|`mgmtp.a12.workflows.automatic-synchronization.enabled` | false | Synchronize A12 document fields to CIB 7 automatically. Alternatively, you may disable this and use the link:/docs/workflows/ba-docs/index.html#anchor-provided-delegates[`syncAvailableFieldsDelegate`] to control when data is synced (e.g. for performance reasons).

|`mgmtp.a12.workflows.extension.asynchronous-mode.enabled` | false | *DEPRECATED* — Enable *asynchronous* communication from Data Services to CIB 7 (see <<anchor-asynchronous-mode, *asynchronous* mode>>). Asynchronous mode is deprecated and will be removed in 2026.06.

|`mgmtp.a12.workflows.extension.asynchronous-mode.consumers.embedded.enabled` | - | *DEPRECATED* — Enables embedded queue consumers. Given no value, embedded consumers are enabled. This must not be set to `false` because embedded is currently the only supported mode. Asynchronous mode is deprecated and will be removed in 2026.06.
|===

=== Object Mapper Configuration

The Workflows Extension requires a `com.fasterxml.jackson.databind.ObjectMapper` containing the `com.fasterxml.jackson.module.kotlin.KotlinModule`. It registers this automatically.

WARNING: Please avoid overriding the object mapper bean. If you do have to, remember to add the Kotlin module. Otherwise, metadata serialization may fail.

[[anchor-workflows-extension-events]]
== Events

We publish the following Spring events to hook into our RPC operations.

WARNING: In <<anchor-asynchronous-mode,async mode>>, the only difference between "before" and "after" events is that a corresponding command has been persisted in the _outbox_ (in the sense of the _outbox pattern_). In other words, even in "after" events, CIB 7 may not have received any request yet.

=== `TaskBeforeAssignEvent`

This event is fired before a _Task_ is assigned to a user and before the corresponding task document is even loaded.

The event is fired with the following parameters:

[source,java]
----
TaskBeforeAssignEvent(DocumentReference docRef, String assignee)
----

You can handle the event as follows:

[source,java]
----
@EventListener
public void handleTaskBeforeAssignEvent(TaskBeforeAssignEvent event) {
    // do something
}
----

==== Use cases

* Prevent assignment of the _Task_.
* Run custom code before _Task_ assign.
* Monitoring, tracing, logging

=== `TaskAfterAssignEvent`

This event is fired after a _Task_ has been successfully assigned to a user (in sync mode).

The event is fired with the following parameters:

[source,java]
----
TaskAfterAssignEvent(DocumentReference docRef, String assignee)
----

You can handle the event as follows:

[source,java]
----
@EventListener
public void handleTaskAfterAssignEvent(TaskAfterAssignEvent event) {
    // do something
}
----

==== Use cases

* Run custom code only after successful _Task_ assign.
* Monitoring, tracing, logging (for only succeeded operations)


=== `TaskBeforeCompleteEvent`

This event is fired before a _Task_ is completed and before the corresponding task document is even loaded.

The event is fired with the following parameters:

[source,java]
----
TaskBeforeCompleteEvent(DocumentReference docRef)
----

You can handle the event as follows:

[source,java]
----
@EventListener
public void handleTaskBeforeCompleteEvent(TaskBeforeCompleteEvent event) {
    // do something
}
----

==== Use cases

* Prevent completion of the _Task_.
* Run custom code before _Task_ completion.
* Monitoring, tracing, logging

=== `TaskAfterCompleteEvent`

This event is fired after a task has been successfully completed (in sync mode).

The event is fired with the following parameters:

[source,java]
----
TaskAfterCompleteEvent(DocumentReference docRef)
----

You can handle the event as follows:

[source,java]
----
@EventListener
public void handleTaskAfterCompleteEvent(TaskAfterCompleteEvent event) {
    // do something
}
----

==== Use cases

* Run custom code only after successful _Task_ completion.
* Monitoring, tracing, logging (for only succeeded operations)


=== `ProcessBeforeStartEvent`

This event is fired before a process is started, i.e., before the request is forwarded to CIB 7 (in sync mode).

The event is fired with the following parameters:

[source,java]
----
ProcessBeforeStartEvent(String processDefinitionKey, String businessKey, JsonNode variables)
----

You can handle the event as follows:

[source,java]
----
@EventListener
public void handleProcessBeforeStartEvent(ProcessBeforeStartEvent event) {
    // do something
}
----

==== Use cases

* Prevent process start (e.g. run custom validations).
* Run custom code before process start.
* Monitoring, tracing, logging

=== `ProcessAfterStartEvent`

This event is fired after a process has been started, i.e. after the process has been started in CIB 7 (in sync mode).

The event is fired with the following parameters:

[source,java]
----
ProcessAfterStartEvent(String processDefinitionKey, String businessKey, JsonNode variables)
----

You can handle the event as follows:

[source,java]
----

    // do something
}
----

==== Use cases

* Run custom code only after successful process start.
* Monitoring, tracing, logging (for only succeeded operations)

== Java Client

We provide a tiny artifact `workflows-extension-client` which provides constants for our RPC method names via `WorkflowsOperationConstants`.

It can be used in conjunction with Data Services' `RpcOperationsClient` and `RequestBuilderFactory` to invoke our RPC operations:

[source,java]
----
requestBuilderFactory
    .newJsonRpc2RequestBuilder()
    .addMethodCall(WorkflowsOperationConstants.START_PROCESS_OPERATION)
    .id(...)
    .putParameter(...)
    .putParameter(...)
    .build()
----

[[anchor-asynchronous-mode]]
== Asynchronous Mode (Deprecated)

WARNING: Asynchronous mode is *deprecated* as of 2025.06 and will be *removed in 2026.06*. Do not adopt it in new projects.

=== Background: Synchronous Mode

CIB 7 stores only _Document References_ ("docRefs"), no actual documents. Data Services is the single source of truth for all documents.

In sync mode, the <<anchor-cbr-workflows-extension,JSON-RPC operations from our Workflows Extension>> manipulate the documents in Data Services and send a request to CIB 7 synchronously, i.e., in the same transaction.

Thus, the changes in Data Services are only committed after the transaction in CIB 7 has been committed.

.In rare cases, using *synchronous* mode can lead to data inconsistencies between Data Services and CIB 7.
[%collapsible]
====
There are two cases where inconsistencies may arise:

. The Workflows Extension calls Data Services API to modify a document. This succeeds and the Workflows Extension calls the CIB 7 REST API. During this request, an exception due to a network problem occurs. The changes in Data Services are rolled back. However, despite network issues, the call to the CIB 7 API was still successful. In this case, the changes in CIB 7 are committed while the changes in the Data Services are rolled back.
. CIB 7 was successful and persisted the changes to its database. A network error occurs while CIB 7 sends its response back to Workflows Extension. Workflows Extension doesn't get a response from CIB 7 and hence assumes that CIB 7 failed, resulting in Data Services rolling back the changes it made.

image:assets/images/transaction_failure_cases_in_synchronous_mode.png[Transaction failure cases in synchronous mode]
====

=== Enabling Asynchronous Mode

*Asynchronous mode* can be enabled via the <<anchor-profile-async-mode,`workflows-async`>> profile. See also <<anchor-workflows-extension-config, Workflows Extension Configuration>>.

Asynchronous mode is based on the _outbox pattern_, which will be explained in detail below.

NOTE: The `businessKey` is necessary to use the *asynchronous* mode.

=== Step-by-Step Comparison Between Synchronous and Asynchronous Communication

In async mode, transactions are committed in Data Services before CIB 7 knows about the request. You can imagine it as "CIB 7 (state) follows Data Services (state)".

Let's look at the `COMPLETE_TASK` JSON-RPC operation.

To be successful, this operation must successfully call Data Services Java API and CIB 7 REST API.

*In synchronous mode...*

. In the `COMPLETE_TASK` operation, Data Services Java API is called synchronously to remove metadata from the document.
. Data Services removes the metadata in the document (but this is not yet committed).
. The CIB 7 REST API is invoked to complete the task.
. CIB 7 completes the task and commits the changes in its database.
. CIB 7 sends a success response to Data Services. Only after this, the Data Services transaction is committed.

image:assets/images/synchronous-communication.png[Synchronous Communication].

*In asynchronous mode*, we have two transactions...

*First transaction:*

. In the `COMPLETE_TASK` operation, Data Services Java API is called synchronously to remove metadata from the document.
. Data Services removes the metadata in the document.
. _Within the same transaction_, an outbox command (technically a JMS message) containing the necessary data to complete a task is persisted.

[NOTE]
====
*Outbox pattern*

* This is the main trick of this _outbox pattern_. Either both operations (modify document and write outbox command) are persisted, or none.
* Technically, we implement outbox commands as JMS messages.
** We reuse the Artemis JMS queue provided by Data Services.
* We use a single queue named `WORKFLOWS_OUTBOX_QUEUE`. All outbox commands are persisted in this queue.
* Here, the message is of type `CompleteTaskOutboxCommand`, which encapsulates the `taskId` and the `businessKey`.
* Messages _with the same businessKey_ are processed in the same order they came in. This is necessary because a different order may lead to invalid operations.
** This is achieved using Artemis _message groups_.

image:assets/images/diagram_queue_messagegroup_consumer.png[Relationship between queue, message group and consumer].
====

*Second transaction:*

. The consumer consumes the message by pulling it out of the queue.
** A consumer is associated with a link:https://activemq.apache.org/message-groups.html[message group].
. The consumer invokes the CIB 7 operation to complete the task.
. CIB 7 tries to complete the task.
. If CIB 7 successfully completes the task, a positive JSON-RPC response is sent to the consumer and the consumer deletes the message from the queue.
. If CIB 7 fails to complete the task, a failure response is sent to the consumer and the message _will not be removed_ from the queue. The consumer will try again later.

image:assets/images/asynchronous-communication.png[Asynchronous Communication].

=== Advantages and Disadvantages of Asynchronous Mode

==== Advantages

* *Eventual consistency* can be achieved because messages are persisted in a JMS queue and only deleted if the respective operation was successful. So messages will be received even if some network errors may occur.
* With multiple consumers, high availability and load balancing can be achieved.

==== Disadvantages

* The update of the UI is still an issue in *asynchronous* mode. For now projects have to handle the UI update themselves.

=== Consumer Scaling

It is highly recommended to enable scaling of your consumers, as the consumers are bottlenecked by CIB 7 responses, which can take arbitrarily long depending on your process.

To scale your consumers, set the properties

* `spring.jms.listener.min-concurrency` and/or
* `spring.jms.listener.max-concurrency`

to appropriate values.

These values will depend on your actual process, the amount of service tasks between async breakpoints in your process, and of course the number of concurrent users for your application, so you will have to experiment with these values.

If you cannot overwrite these values for whatever reason, you can register your own `DefaultJmsListenerContainerFactory` with something like this:

[source,java]
----
class CustomFactory: DefaultJmsListenerContainerFactory(){
    override fun initializeContainer(container: DefaultMessageListenerContainer) {
        super.initializeContainer(container)
        if (container.destinationName == WORKFLOWS_OUTBOX_QUEUE) {
            container.minConcurrentConsumers = ...
            container.maxConcurrentConsumers = ...
        }
    }
}
----
