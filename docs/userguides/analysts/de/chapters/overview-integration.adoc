= Übersicht der Integrationsmöglichkeiten

Erfolgreiche Modellierung und Integration von Workspaces, die Workflows nutzen, erfordert im Vergleich zu einem Standard-CRUD-Anwendungsfall einige zusätzliche Überlegungen:

* Korrekte Konfiguration Ihrer Anwendung
* Gültige(s) BPMN-Modell(e)
* Document Models, die in einem Task verwendet werden, müssen Prozess-Metadaten speichern können
** Field-Werte, die im Prozess verwendet werden, müssen korrekt annotiert sein
* Form Model Actions müssen so konfiguriert sein, dass der Prozess-Token entsprechend weiterbewegt wird
* Overview Model Actions müssen so konfiguriert sein, dass sie sowohl einen Prozess starten als auch neue Dokumente erstellen

=== Aktuelle BPMN-Einschränkungen

==== Parallele Tasks

[WARNING]
====
Parallele _Tasks_ können nicht dasselbe Dokument referenzieren.

Anders ausgedrückt: Ein Dokument kann jeweils nur von einem _User Task_ gleichzeitig referenziert werden.
====

==== Signal Events

[[anchor-cbe]]
==== Conditional Boundary Events

A12 Workflows unterstützt grundsätzlich die Verwendung von _Conditional (Boundary) Events_ (siehe auch link:https://docs.cibseven.org/manual/{cibsevenVersion}/reference/bpmn20/events/conditional-events/[CIB 7 Manual: Conditional Events]).

_Conditional (Boundary) Events_ können auf Prozessvariablen aus Document Fields lauschen, die mit *availableInProcessAs* annotiert sind (siehe <<anchor-cbr-synchronize-values>>). Beachten Sie jedoch die nachfolgend beschriebenen Fallstricke.

===== Fallstricke

. Wenn ein _User Task_ über ein _Boundary Event_ beendet wird, beachten Sie bitte, dass die Benutzeroberfläche nicht automatisch neu geladen wird – anders als beim Abschluss eines Tasks über das `proceed`-Formularereignis.

. _Conditional Boundary Events_ sollten ausschließlich auf externe Datenänderungen reagieren. Änderungen, die ein Benutzer während der Bearbeitung des User Tasks vornimmt, sollten das _Conditional Boundary Event_ also nicht auslösen.
** Der Grund: Das Abschließen eines Tasks über die Benutzeroberfläche verursacht ebenfalls eine Datenänderung. Falls diese Task-Fertigstellung das Boundary Event auslöst, versucht die Engine, den Task abzuschließen, der bereits durch das _Conditional Boundary Event_ gelöscht wurde. Dies führt zu sporadischen Fehlern (Race Conditions).

NOTE: Camunda Modeler-Versionen vor 5.12.0 haben einen Fehler, der das Setzen von Ereignistypen für Conditional Events verhindert. Falls Sie davon betroffen sind, aktualisieren Sie bitte auf eine neuere Version des A12 Installers.

[[anchor-element-templates]]
=== Camunda Element Templates

Camunda bietet die Möglichkeit, _Element Templates_ zu erstellen, die maßgeschneiderte Ansichten auf BPMN-Elemente bereitstellen.

Durch die Verknüpfung eines solchen _Element Templates_ wird das Eigenschaftenpanel für das jeweilige Element angepasst. Der Modeler erhält so eine maßgeschneiderte Ansicht der vorzunehmenden Einstellungen.

[NOTE]
====
Workflows stellt <<anchor-provided-element-templates,_Element Templates_>> zur Unterstützung der Modellintegration bereit.

Diese Templates enthalten maßgeschneiderte Ansichten und eine einfache Validierung der Einstellungen.
====

Beispielsweise würde ein _Element Template_ für einen _Service Task_, der einen bestimmten Delegate aufruft, nur die relevanten Eigenschaften für diesen Delegate anzeigen:

* Die Referenz auf den Delegate ist voreingestellt
* Die Namen der Eingabeparameter sind vordefiniert

Der Modeler muss lediglich die Eingabewerte angeben.
In bestimmten Fällen werden die Eingabewerte validiert.
Wenn beispielsweise ein Ausdruck zur Referenzierung einer Prozessvariablen eingegeben werden muss, wird die Eingabe auf korrekte Syntax geprüft.

_Element Templates_ verbessern die Integration von Modellen erheblich, indem sie Zeit sparen und Fehler durch manuelle Eingaben reduzieren.

NOTE: Allgemeine Informationen zu Camunda _Element Templates_ finden Sie in der link:https://docs.camunda.io/docs/components/modeler/desktop-modeler/element-templates/about-templates/[Camunda Docs: Element Templates].

=== BPMN Errors

In CIB 7 können Sie _Error Events_ verwenden, um auf Fehler zu reagieren, die in einem Prozess auftreten. Diese werden als BPMN Errors bezeichnet (siehe auch link:https://docs.cibseven.org/manual/{cibsevenVersion}/reference/bpmn20/events/error-events/[CIB 7 Docs on BPMN Errors]).

[[asnychronous-continuations]]
=== Asynchrone Fortsetzungen

Bei den meisten BPMN-Elementen finden Sie `Asynchronous continuations` im Eigenschaftenpanel.

Diese stellen einen *„Sicherungspunkt"* im Prozess dar.
Tritt ein Fehler auf, setzt CIB 7 auf den letzten „Sicherungspunkt" zurück.

NOTE: User Tasks sind standardmäßig Sicherungspunkte. Service Tasks hingegen nicht.

.Eigenschaftenpanel mit asynchroner Fortsetzung „Before"
image::assets/images/bpmn-asynchronous-before.png[Eigenschaftenpanel mit asynchroner Fortsetzung „Before"]

Asynchrone Fortsetzungen:: Sicherungspunkte können auf `Before` oder `After` gesetzt werden:
+
* `Asynchronous before`
** Setzt einen „Sicherungspunkt" vor dem Element.
** Beispiel: Wenn ein _Gateway_ auf „asynchronous before" gesetzt ist, kann CIB 7 bei einem Auswertungsfehler nicht auf ein Element vor dem _Gateway_ zurückrollen.
* `Asynchronous after`
** Setzt einen „Sicherungspunkt" nach dem Element.
** Beispiel: Wenn ein _Service Task_ auf „asynchronous after" gesetzt ist, kann CIB 7 nicht über diesen Punkt hinaus zurückfallen. Der Service Task wird nicht wiederholt.

[NOTE]
====
Wenn für einen _User Task_ keine asynchrone Fortsetzung angegeben ist, kann CIB 7 bei einem Fehler in einem nachfolgenden Schritt in den Wartezustand dieses User Tasks zurückfallen.
====

[TIP]
====
Als Modeler sollten Sie `exclusive` stets aktiviert lassen.

Asynchrone Fortsetzungen, die über eines der bereitgestellten <<anchor-provided-element-templates,_Element Templates_>> modelliert werden, sind auf `exclusive` gesetzt.
====

== Document Models

[[anchor-metadata-include]]
=== Metadaten-Include

NOTE: Workflow-Metadaten werden derzeit separat von den _Document-Metadaten_ verwaltet.

Sie müssen link:assets/files/WorkflowsMetadata_DM.json[`WorkflowsMetadata_DM.json`] als Include in allen Document Models hinzufügen, die in einem Workflow verwendet werden. Das Include kann auf jeder Ebene liegen, muss aber exakt `A12WF` heißen.

Zur Laufzeit verbinden diese Metadaten ein Dokument mit einem _User Task_ einer laufenden Prozessinstanz.

Die Metadaten werden jedes Mal aktualisiert, wenn ein _User Task_ erstellt, zugewiesen, abgeschlossen oder abgebrochen wird.

Die Metadaten enthalten hauptsächlich folgende Informationen:

* Den Namen des Prozessmodells,
* die Prozessinstanz-ID,
* den Business Key für diese Prozessinstanz,
* den Initiator, der diese Prozessinstanz gestartet hat,
* den Namen und die ID des aktuellen _User Tasks_,
* den Assignee des aktuellen _User Tasks_,
* den Namen des _Form Models_, das mit einem _User Task_ verknüpft ist.

[CAUTION]
====
Die in den Workflow-Metadaten verwendeten String-Daten werden validiert, um sicherzustellen, dass die verwendeten Zeichen in den im Document Model definierten link:/docs/sme/sme-dm-ba-docs/index.html#txt:reference:supported-characters[Supported Characters] enthalten sind.

Die Modellierung eines eingeschränkten Zeichensatzes bei den Supported Characters kann zu formalen Validierungsfehlern beim Hinzufügen oder Aktualisieren der Workflow-Metadaten führen. Dies verhindert das Speichern des Dokuments.
====

[[anchor-cbr-context-based-validation-rules]]
=== Kontextbasierte Validation Rules

Um eine erfolgreiche Validierung von „Zwischendokumenten" zu ermöglichen, die während eines Prozesses aufgebaut werden, müssen Modeler *_kontextbasierte Validation Rules_* schreiben.
Die Idee ist, dass in verschiedenen Phasen eines Prozesses unterschiedliche Validation Rules aktiv werden sollen.

[CAUTION]
====
Standardmäßig wird eine Full Validation für alle Dokumente durchgeführt – auch beim Bearbeiten oder Abschließen eines Tasks.
====

[TIP]
====
Um den Modellierungsaufwand zu reduzieren, sollte der Status eine Enumeration sein. Mithilfe von _link:/docs/sme/sme-dm-ba-docs/index.html#_enumeration_categories[Kategorien,role=internal]_ können mehrere Enumerationswerte zu einer Kategorie zusammengefasst werden.

Auf diese Weise können Sie „Validierungsstufen" definieren, wobei jede Kategorie eine solche Stufe repräsentiert.
In jeder Stufe gelten unterschiedliche Validation Rules.
====

==== Beispiel

Betrachten Sie ein einfaches Modell mit drei Fields:

.Einfaches Modell
[%header, cols="1,1,2a"]
|===
|Field|Datentyp|Datentyp-Einschränkungen
|Name|String|-
|DateOfBirth|Date|-
|Status|Enumeration|
Category = "RuleCategory"

[%header, cols="1,1"]
!===
!Enumerationswert!RuleCategory
!StartingStatus!Start
!NameMustBeFilled!BothRules
!DateOfBirthMustBeFilled!BothRules
!===

|===

Das Field „Status" kann die drei in der Tabelle dargestellten Werte annehmen.

Fügen wir nun folgende Validation Rules hinzu:

.Im einfachen Modell modellierte Rule
[%header, cols="1,1,2a"]
|===
|Rule|Error Field|Fehlerbedingung
|NameIsFilled
|Name
|`[Status -> RuleCategory] == "BothRules" AND FieldNotFilled(Name)`
|DateOfBirthIsFilled
|DateOfBirth
|`[Status] == "DateOfBirthMustBeFilled" AND FieldNotFilled(DateOfBirth)`
|===

Im Prozess aus <<bpmn-status-based-validation>> findet folgende kontextbasierte Validierung statt:

. Der Status wird auf „NameMustBeFilled" gesetzt.
. Der Benutzer füllt den Namen im User Task „Enter Name" aus.
.. Wenn der Name leer bleibt, greift die Rule „NameIsFilled", da die RuleCategory von „NameMustBeFilled" == „BothRules" ist.
.. Wenn das Geburtsdatum leer bleibt, greift keine Rule.
. Der Status wird auf „DateOfBirthMustBeFilled" gesetzt.
.. Wenn der Name leer bleibt, greift die Rule „NameIsFilled", da die RuleCategory von „DateOfBirthMustBeFilled" == „BothRules" ist.
.. Wenn das Geburtsdatum leer bleibt, greift die Rule „DateOfBirthIsFilled".

[[bpmn-status-based-validation]]
.Unterschiedliche Validation Rules, die durch Kontextänderungen ausgelöst werden
image::assets/images/bpmn-status-based-validation.png[Unterschiedliche Validation Rules, die durch Kontextänderungen ausgelöst werden]

[[anchor-cbr-synchronize-values]]
=== Synchronisierung von Field-Werten

Field-Werte können von einem Dokument zum entsprechenden _User Task_ in CIB 7 synchronisiert werden.

Dazu müssen Sie die gewünschten Fields mit `*availableInProcessAs*` annotieren und den gewünschten Namen der _Prozessvariablen_ angeben.

Bei aktivierter automatischer Synchronisierung findet die Synchronisierung immer dann statt, wenn sich die Dokumentdaten ändern. Sie wird _nicht_ ausgelöst, wenn nur die A12-Workflow-Metadaten geändert werden. Die Synchronisierung erfolgt unter anderem, wenn...

* ein _User Task_ gespeichert wird.
* ein _User Task_ über das `proceed`-Ereignis abgeschlossen wird.
* ein _User Task_ einem Benutzer zugewiesen wird.
* das Dokument extern geändert wird, z. B. per Code.

NOTE: Derzeit können nur Fields zu CIB 7 synchronisiert werden. Bei wiederholten Fields wird der zuletzt gefundene Wert synchronisiert.

[[anchor-overview-models]]
== Overview Models

Overviews im Kontext von A12 Workflows repräsentieren *Aufgabenlisten*.

Eine Aufgabenliste kann Tasks eines oder mehrerer Prozessmodelle anzeigen.
Es kann auch eine heterogene Aufgabenlisten-Overview modelliert werden.

Ein Eintrag in einer Aufgabenliste ist ein aktuell aktiver _User Task_ in einer aktuell laufenden _Prozessinstanz_.

Das Overview Model *muss ein Document Model referenzieren, das unsere `WorkflowsMetadata_DM.json` enthält*.

WARNING: Wir liefern keine Overview-Komponente standardmäßig aus. *Das Folgende hängt daher von der Overview-Implementierung des Projekts ab.* Es beschreibt jedoch *die gängigste Situation*.

. Stellen Sie in der `VIEW_ADD`-Directive sicher, dass der Name mit dem Namen der registrierten Overview-Komponente übereinstimmt.

[[anchor-RBAC-modeling]]
== RBAC-Modellierung

NOTE: RBAC = Role-Based Access Control.

Obwohl Modeler mit RBAC _bestimmte_ CRUD-Anwendungsfälle abbilden können, ist dieser modellbasierte Autorisierungsmechanismus nicht für Workflow-bezogene Anwendungsfälle geeignet.

=== Einschränkungen der RBAC-Modellierung

* RBAC ermöglicht Zugriffsregeln nur auf Modellebene
* Es lassen sich keine sinnvollen Aufgabenlisten anzeigen
** Beispiel: Wenn ein Benutzer seinen eigenen Vertrag sehen soll, kann er alle Verträge sehen

[NOTE]
====
Anwendungsfälle, die für Workflows relevant sind (z. B. „Ich sehe in der Aufgabenliste nur meine eigenen Urlaubsanträge"), lassen sich mit ABAC (Attribute-Based Access Control) umsetzen.
ABAC ist derzeit nicht modellbasiert.
====

[[anchor-cdm-integration]]
== CDM-Integration

Workflows unterstützt das Öffnen von CDM-basierten Formularen aus einer _Aufgabenübersicht_.

Nehmen wir an, wir arbeiten mit folgenden Modellen:

* Document Model `Team_DM` als Root-Document Model des CDM
* Document Model `Employee_DM`
* Relationship Model `TeamEmployee_RM`, das die Beziehung zwischen `Team_DM` und `Employee_DM` definiert
** Ein Team kann bis zu 10 Mitarbeiter haben
** Ein Mitarbeiter kann nur in einem Team sein
* Composed Document Model `TeamEmployee_CDM`

WARNING: Das Root-Document Model muss unsere <<anchor-metadata-include,Workflow-Metadaten>> enthalten.

Die folgenden Schritte beschreiben, wie Overview Model, Form Model und App Model eingerichtet werden:

* Stellen Sie im link:/docs/OVERALL/relationships_for_bas/index.html#_simple_composed_data[CDM,role=internal] `TeamEmployee_CDM` sicher, dass das Root-Document Model für das Annotationsfeld `cdm.queryRoot` in den Modelleinstellungen des CDM korrekt definiert ist. In unserem Beispiel wäre dies `cdm.queryRoot: Team_DM`.
* Erstellen Sie ein link:/docs/OVERALL/relationships_for_bas/index.html#_cdms_and_regular_overviews_or_trees[Overview Model,role=internal], das das CDM referenziert. In unserem Beispiel wäre dies `TeamPerson_CDM`.
* Erstellen Sie ein link:/docs/OVERALL/relationships_for_bas/index.html#_modeling_a_form_model_for_a_cdm[Form Model, das das CDM referenziert,role=internal]. In unserem Beispiel kann das Form Model `TeamEmployee_CFM` heißen und würde `TeamPerson_CDM` referenzieren.
* Erstellen Sie ein link:/docs/OVERALL/relationships_for_bas/index.html#appmodel_link[App Model für CDMs,role=internal].
** Für Workflows müssen Sie die <<anchor-overview-scene,Overview Scene anpassen>>.
** Außerdem müssen Sie die <<anchor-cdm-task-overviews,Form Scenes für CDM-Aufgabenübersichten>> modellieren.
